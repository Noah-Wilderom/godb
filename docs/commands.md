# Logical database commands

`EncodeCommand`, `DecodeCommand`, and `db.ApplyCommand` define a versioned logical
mutation boundary for future replication. A command contains an ordered list of
operations that succeeds or rejects as one transaction through the existing writer
and WAL. It contains no page IDs, database UUID, local transaction revision, clock
read, or generated identifier. Each database derives its own primary/index entries
and page changes from the supplied operations.

```go
command := database.Command{Operations: []database.CommandOperation{
    {Kind: database.CommandCreateTable, Table: &table},
    {Kind: database.CommandInsertRow, Table: &table, Row: firstRow},
    {Kind: database.CommandInsertRow, Table: &table, Row: secondRow},
}}

encoded, err := database.EncodeCommand(command)
if err != nil {
    return err
}
result, err := db.ApplyCommand(encoded)
if err != nil {
    return err
}
if result.Code != database.CommandOK {
    // Handle the explicit command rejection.
}
```

The example executes locally. There is no Raft proposal, network transport, or
replication in this API yet. A future leader must propose encoded bytes through
consensus; a follower must not independently invoke client mutations.

## Operations

| Kind | Required fields | Behavior |
| --- | --- | --- |
| `CommandPut` | `Key`, `Value` | Raw key insert or replacement |
| `CommandDelete` | `Key` | Raw key deletion; missing key succeeds |
| `CommandCreateTable` | `Table` | Register an explicit table ID and name |
| `CommandInsertRow` | `Table`, `Row` | Insert a primary row and its indexes |
| `CommandUpdateRow` | `Table`, `Row` | Replace an existing row with the same primary key |
| `CommandPatchRow` | `Table`, `PrimaryKey`, partial `Row` | Merge assignments into the current row at apply time; maintain indexes atomically |
| `CommandDeleteRow` | `Table`, `PrimaryKey` | Delete a row and its derived index entries; legacy zero result counts |
| `CommandDeleteRowCounted` | `Table`, `PrimaryKey` | Delete with commit-time removed-row counts; NULL key is a no-op |

`Table` and `PrimaryKey` are pointers. Unused fields must be absent or empty.
Empty raw keys and values are allowed. An update or delete of a missing row is a
successful no-op. `CommandResult.AffectedRows` and `MatchedRows` sum changed/matched
rows for successful patch and counted-delete operations; legacy command kinds still leave these
fields zero. Any rejection clears both counts for the complete atomic command.

Typed operations include the complete expected table definition and check it
against the catalog at execution. This supports creating a table and using it
later in the same command. Index entries are generated by the engine, not accepted
as typed-operation inputs. Raw key operations retain their low-level behavior and
can bypass relational invariants; do not expose them as an unrestricted SQL API.

Commands allow 1..64 operations with the existing total reservation limit of 64
key mutations, including secondary indexes and update reservations. A command is
never split into separate writer groups. At most 1 MiB of encoded input is accepted;
the underlying row, entry, catalog, and staged-page limits also apply.

## Deterministic encoding and application

Encoding copies and sorts schema columns and indexes by ID. It preserves the
order of columns inside an index, which determines composite-key semantics.
Zero-index tables normalize an empty index slice to nil. Catalog JSON uses the
existing canonical field representation. Rows and values use their existing binary
encodings, including sorted row-column IDs and record-map keys. Operation order
is preserved. JSON record values retain their validated payload representation;
the command layer does not normalize arbitrary JSON document whitespace.

The decoder bounds counts and lengths, rejects unsupported versions and kinds,
rejects trailing bytes, validates every operation, and checks exact canonical
re-encoding. Unknown/duplicate schema fields, noncanonical whitespace, and unsorted
schema lists are rejected. Decoded values own their buffers. Do not mutate input
objects or encoded bytes concurrently with a call that consumes them.

Given the same valid logical starting state and the same ordered commands,
databases produce the same logical rows, indexes, and result codes. Database UUIDs,
physical page layout, file bytes, and statistics need not match. Commands generate
no table IDs, timestamps, UUID values, or random row data: choose such values before
encoding. Do not make command semantics depend on map iteration order or local
configuration. Incompatible codec or semantic changes require a new command version.

## Results versus failures

`ApplyCommand` decodes and validates the entire input before submitting any work.
Malformed or oversized input returns an error matching `ErrInvalidCommand` and
does not reach the writer. A valid command returns one of these stable codes:

| Code | Meaning |
| --- | --- |
| `ok` | All mutations completed, or all operations were successful no-ops |
| `duplicate_primary_key` | A primary row already exists |
| `unique_conflict` | A unique index value belongs to another row |
| `table_id_exists` | The table ID is already registered |
| `table_name_exists` | The table name is already registered |
| `table_not_found` | A required table is absent |
| `schema_mismatch` | The expected definition differs from the stored table |
| `mutation_limit` | Runtime update preparation exceeds the mutation budget |
| `invalid_update` | The row produced by a patch exceeds row/key storage constraints |

Expected rejections return a non-`ok` code and **nil Go error**. They discard every
earlier staged mutation in that command, including splits and new catalog entries,
without poisoning the handle. Always inspect `result.Code` as well as `err`.
The existing writer statistics still count a logical rejection as a write error.

I/O failures, corruption, and a closed handle return a Go error and an empty result
code. They must not be converted into an ordinary replicated rejection. In particular,
`ErrWriteFailed` takes precedence over any wrapped cause. A future replica must stop
application on a storage failure rather than pretend that a log entry was applied.
After durable WAL logging, a failed/unacknowledged command may still recover in full;
the usual [recovery semantics](recovery.md) apply.

## Remaining replication work

`ApplyCommand` alone does not track a log index or deduplicate requests. For ordered
replay, use [ApplyLogEntry](log-application.md): it atomically persists application
position, request digests, and outcomes with the mutations, including deterministic
rejections and no-ops. Its additional `request_id_conflict` result rejects reuse of
a request ID with different command bytes.

On an unbound database, applying the same command twice is another attempt: a
second table creation rejects, while a raw put may succeed again. After the first
`ApplyLogEntry` commit binds a database to a group, ordinary mutation APIs and
`ApplyCommand` return `ErrReplicatedWriteRequired`. A future replicated server must
route mutations through its ordered committed log. Raft's own durable log/hard
state, transport, membership, consistent replicated reads, snapshot installation,
and cross-shard transactions remain separate features.

Local `WriteTx` read revisions cannot be copied into a command: they depend on one
handle's write grouping and lifetime. There is deliberately no automatic export of
read-dependent transactions. Replicated read-modify-write work will need portable
preconditions or another concurrency protocol tied to replicated state. Simply
reading locally and proposing an unconditional update does not preserve the local
transaction's conflict checks.

## Wire format 1

All integers are little endian. The first eight bytes are `GODBCMD1`, followed by
a two-byte operation count. Each operation contains:

1. One-byte kind: put `0x01`, delete `0x02`, create table `0x03`, insert row `0x04`,
   update row `0x05`, delete row `0x06`, patch row `0x07`, counted delete row `0x08`.
2. Four-byte schema length and that many canonical JSON bytes; zero for raw operations.
3. Four-byte payload length and that many payload bytes.

Put payloads contain a four-byte key length, the key, and the value as the remaining
bytes. Delete payloads contain just the key. Create-table payloads are empty.
Insert/update payloads use row format 1. Delete-row payloads use the existing record
value encoding for the primary key. The command has no checksum or authentication
layer; durable log framing and transport integrity are separate responsibilities.

## Partial-row command encoding

`CommandPatchRow` adds kind `07` to the existing GODBCMD1 envelope. Its table field
uses the usual canonical schema JSON. Its payload is a record ARRAY containing
exactly `[primary_key, assignments]`, where assignments is a record MAP from
canonical decimal column IDs to values. Record-map ordering makes assignment order
irrelevant to command bytes. The decoder rejects unknown IDs, primary-key
assignments, empty patches, wrong types/nullability, and noncanonical encodings.
A NULL key represents an UPDATE equality predicate that cannot match.

The writer reads the row only when applying the committed command, preserves
unassigned columns, and derives new indexes using the existing update planner.
Patch reservations are `min(1 + 2*indexCount, 64)`, like full-row updates. Resulting
row/key capacity failures are deterministic rejections rather than storage failures.
New binaries continue to decode existing commands. Older binaries do not understand
kind 07; this addition is not a mixed-version rolling-upgrade protocol.

## Counted row deletion

`CommandDeleteRowCounted` adds kind `08`. Its payload is the canonical record
encoding of the primary key, as with legacy kind `06`, but NULL means no match.
It reserves `1 + indexCount` mutations and derives the current row's index keys at
application. Removing a row contributes 1 to both AffectedRows and MatchedRows;
missing/NULL keys contribute zero. Counts are cleared if the enclosing command
rejects. Legacy kind `06` keeps its original behavior and does not accept NULL.
Kind `08` requires updated binaries on every replica; no mixed-version negotiation
is implemented. Nonzero results use the existing version-2 log/request records.
